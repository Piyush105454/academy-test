Wireframes — consent workflow & risk view

Layout and logic only. Grey boxes, no colours, no branding — these are for agreeing what the screens do, before anyone designs what they look like.

Not implemented. Nothing here is built.

No code exists for these screens and none should be written until the flow below is agreed with WES. The consent gate in the agent is real and already refuses to run without a record — but nothing yet creates that record. That gap is the whole point of this page.

Four screens. The rule that shapes all of them: consent is collected once from the family at enrolment, not clicked through by a teacher before each batch.

A screen for whoever owns the agent at WES — not for teachers. One row per risk, its current state, and who is holding it.

Rows marked "enforced" are covered by automatic checks that run on every code change. Rows marked "manual", "open" or "decision" are not — they depend on a person, which is exactly why they are on a screen rather than in a document.
Three things to settle before any of this is built. Who sends the consent request — the school office or the class teacher? · What happens to a student whose guardian never responds: hand-marking forever, or a reminder cycle? · When a family withdraws consent, do past marks disappear too, or only future ones?
